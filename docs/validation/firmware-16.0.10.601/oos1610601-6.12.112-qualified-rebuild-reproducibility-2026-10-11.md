The physically qualified `.601` boot instead contains:

## Decision

The build environment reproduces the qualified machine image byte-for-byte
outside the expected autogenerated certificate and dependent build ID. It also
reproduces the qualified config, symbol versions, release string, DTB config,
boot layout, and verified `.601` AVB contract.

The normalized rebuilt-qualified-source control physically passes both
Android FBE/user0 and the TWRP PIN oracle. This proves that the current build
environment can produce a functional kernel from the exact qualified source;
the generated certificate/build-ID difference is not sufficient to reproduce
the failure.

It still does **not** prove that packaging drift is the sole cause of the
failed security candidates. Those candidates were built with a different boot
security-patch/fingerprint contract, so an immediate source bisect remains
premature until that variable is removed.

Next safe sequence:

1. normalize the no-NTFS security candidate to this exact `.601` boot
   contract;
2. with explicit authorization, test that normalized candidate using the same
   Android and TWRP FBE oracles;
3. begin a source bisect only if the normalized no-NTFS security candidate
   still fails.

No source commit, push, release, or security-series bisect was made by this
phase. The phone was left on the exact qualified boot.
